# 창고 설계 — SQLite

수집한 것을 담는 곳이다. **지도가 아니다.**
지도는 창고에서 "관계가 붙은 것" 만 꺼내 그린다.

구현 전 설계 문서다. 아직 코드는 없다.

---

## 0. 먼저 확인한 것

### RST_MONA_CD 는 NAAS_CD 와 같은 체계다 — 실물로 확인

probe 로 받은 실제 응답에서 조인이 성립했다.

| 출처 | 필드 | 값 | 이름 |
|---|---|---|---|
| `ALLNAMEMBER` | `NAAS_CD` | `T2T8225E` | 강경숙 |
| `nzmimeepazxkubdpn` | `RST_MONA_CD` | `T2T8225E` | 강경숙 |

표본 3건 × 3건에서 **겹치는 의원이 한 명 있었고 코드가 일치했다.**
모든 코드가 `[0-9A-Z]{8}` 로 같은 모양이다 (28개 전부).

**한계: 확인된 건 1쌍이다.** 우연일 확률은 낮지만 (8자리 영숫자 + 이름 동시 일치),
전량 수집 후 아래를 반드시 돌려야 한다.

```sql
-- 발의법률안에 나온 코드 중 의원 명부에 없는 것
SELECT DISTINCT p.member_cd, p.member_nm
FROM bill_proposer p LEFT JOIN member m ON m.cd = p.member_cd
WHERE m.cd IS NULL;
```

0건이어야 한다. 0이 아니면 그만큼이 **이름으로도 코드로도 못 붙는 의원**이다.
`0` 을 그냥 믿지 말고 분모를 같이 낸다 — `미매칭 0 / 대조 18,862건`.

### 이름 조인은 아예 두지 않는다

동명이인이 실제로 있다. 위 표본에도 **강경숙 · 강경식** 이 나란히 있었다.
`member_nm` 은 화면 표시용으로만 저장하고, **조인 키로 쓰는 코드 경로를 만들지 않는다.**

## 1. 층을 나눈다 — 원본층 · 가공층

매퍼가 틀린 걸 나중에 발견해도 **다시 안 긁어도 되게** 한다.

```
   API ─→ [원본층] raw_fetch · raw_row      ← 받은 그대로. 절대 안 고친다
                     │
                     ↓ 매퍼 (언제든 다시 돌린다)
          [가공층] member · bill · bill_proposer · vote_tally
                     │
                     ↓ 규칙 (언제든 다시 돌린다)
          [관계층] link
                     │
                     ↓ 내보내기
                    지도
```

**가공층과 관계층은 언제든 통째로 DROP 하고 원본층에서 다시 만들 수 있어야 한다.**
이게 안 되면 층을 나눈 의미가 없다. 그래서 아래 규칙을 둔다.

- 가공층 테이블에는 **사람이 손으로 넣은 값이 없다.** 전부 매퍼가 만든다.
- 손으로 고친 게 필요하면 `override` 테이블에 따로 두고 매퍼가 마지막에 덮는다.
- 재생성 검사: `DROP → 재구축 → 행 수와 체크섬 비교`. 다르면 매퍼가 비결정적이다.

## 2. 원본층

```sql
-- 한 번의 API 호출. 무엇을 언제 어떤 파라미터로 불렀는가.
CREATE TABLE raw_fetch (
  id          INTEGER PRIMARY KEY,
  service     TEXT NOT NULL,          -- 'nzmimeepazxkubdpn'
  params      TEXT NOT NULL,          -- '{"AGE":"22","pIndex":3}' 정렬된 JSON
  fetched_at  TEXT NOT NULL,          -- ISO8601
  status      INTEGER,                -- HTTP
  code        TEXT,                   -- 'INFO-000' / 'ERROR-300' / 'ERROR-310'
  total       INTEGER,                -- list_total_count
  body        BLOB NOT NULL           -- 응답 원문 (gzip)
);
CREATE UNIQUE INDEX raw_fetch_key ON raw_fetch(service, params);

-- 응답에서 뽑은 행 하나. 여전히 원본 JSON 그대로다.
CREATE TABLE raw_row (
  id        INTEGER PRIMARY KEY,
  fetch_id  INTEGER NOT NULL REFERENCES raw_fetch(id),
  service   TEXT NOT NULL,
  natural_k TEXT NOT NULL,            -- 서비스별 자연키 (BILL_ID · NAAS_CD 등)
  row_json  TEXT NOT NULL
);
CREATE UNIQUE INDEX raw_row_key ON raw_row(service, natural_k);
```

**`body` 를 지우지 않는다.** 매퍼가 `row_json` 을 잘못 뽑았을 수도 있다.
원문이 있으면 다시 뽑을 수 있고, 없으면 다시 긁어야 한다.

`params` 는 **키 정렬한 JSON 문자열**로 만든다. 같은 호출을 두 번 저장하지 않기 위해서다.

## 3. 가공층

### 의원

```sql
CREATE TABLE member (
  cd        TEXT PRIMARY KEY,         -- NAAS_CD. 유일한 조인 키
  nm        TEXT NOT NULL,            -- NAAS_NM. 표시용
  nm_hanja  TEXT,                     -- NAAS_CH_NM. 동명이인 구분 참고용
  party     TEXT,                     -- PLPT_NM 의 마지막 값 (현재 정당)
  party_all TEXT,                     -- PLPT_NM 원문 ('유신정우회/유신정우회')
  eraco     TEXT,                     -- GTELT_ERACO ('제9대, 제10대')
  district  TEXT,                     -- ELECD_NM
  cmit      TEXT,                     -- BLNG_CMIT_NM
  pic_url   TEXT,                     -- NAAS_PIC
  src_row   INTEGER REFERENCES raw_row(id)
);
```

`PLPT_NM` 이 `'유신정우회/유신정우회'` 처럼 **슬래시로 이력이 붙는다.**
현재 정당은 마지막 조각이다. 원문도 같이 남긴다 — 정당 이력이 나중에 쓸모 있다.

**`party` 를 진영(`side`)으로 바꾸는 표는 별도 테이블에 둔다.** 코드에 박지 않는다.

```sql
CREATE TABLE party_side (
  party TEXT PRIMARY KEY,
  side  TEXT NOT NULL,                -- 'blue' | 'red' | 'gov' | 'gold'
  src   TEXT NOT NULL                 -- 왜 이렇게 분류했나
);
```

### 법안

```sql
CREATE TABLE bill (
  bill_id     TEXT PRIMARY KEY,       -- BILL_ID
  bill_no     TEXT,                   -- BILL_NO
  nm          TEXT NOT NULL,
  age         INTEGER NOT NULL,       -- 대수
  committee   TEXT,
  propose_dt  TEXT,                   -- 발의일
  proc_dt     TEXT,                   -- 본회의 처리일
  proc_result TEXT,
  announce_dt TEXT,                   -- 공포일. 규칙 3 의 유일한 입력
  detail_url  TEXT,
  src_row     INTEGER REFERENCES raw_row(id)
);
CREATE INDEX bill_age ON bill(age);
CREATE INDEX bill_announce ON bill(announce_dt);
```

### 발의자 — 대표와 공동을 한 테이블에 두되 종류로 나눈다

```sql
CREATE TABLE bill_proposer (
  bill_id   TEXT NOT NULL REFERENCES bill(bill_id),
  member_cd TEXT NOT NULL,            -- RST_MONA_CD 또는 PUBL_MONA_CD 의 한 조각
  member_nm TEXT,                     -- 표시·검증용. 조인에 쓰지 않는다
  kind      TEXT NOT NULL,            -- 'rst'(대표) | 'publ'(공동)
  ord       INTEGER,                  -- PUBL_MONA_CD 안에서의 순서
  PRIMARY KEY (bill_id, member_cd)
);
CREATE INDEX bp_member ON bill_proposer(member_cd, kind);
```

`PUBL_MONA_CD` 는 쉼표로 붙어 온다. **저장할 때 쪼갠다.**
문자열째로 두면 나중에 `LIKE '%코드%'` 로 조회하게 되고, 그건 틀린 결과를 낸다
(`YM42715P` 가 `AYM42715PZ` 에도 걸린다).

### 본회의 표결 — 지금은 총계만 있다

```sql
CREATE TABLE vote_tally (
  bill_id  TEXT PRIMARY KEY REFERENCES bill(bill_id),
  total    INTEGER,                   -- VOTE_TCNT
  yes      INTEGER,                   -- YES_TCNT
  no       INTEGER,                   -- NO_TCNT
  blank    INTEGER,                   -- BLANK_TCNT
  proc_dt  TEXT,
  src_row  INTEGER REFERENCES raw_row(id)
);

-- 개인별 표결. 아직 못 받았다. 자리만 만들어 둔다.
CREATE TABLE vote_member (
  bill_id   TEXT NOT NULL,
  member_cd TEXT NOT NULL,
  result    TEXT NOT NULL,            -- 찬성 | 반대 | 기권 | 불참
  party     TEXT,                     -- 표결 당시 정당. member.party 와 다를 수 있다
  src_row   INTEGER REFERENCES raw_row(id),
  PRIMARY KEY (bill_id, member_cd)
);
```

**`vote_member.party` 를 따로 저장하는 이유:** 의원은 당을 옮긴다.
표결 당시 정당을 `member` 에서 끌어오면 **나중에 탈당한 의원의 과거 표결이
현재 당의 표결로 바뀐다.** 그건 사실 왜곡이다.

## 4. 관계층 — 선마다 "어느 규칙이 만들었는가"

```sql
CREATE TABLE link (
  id        INTEGER PRIMARY KEY,
  from_id   TEXT NOT NULL,            -- 노드 id
  to_id     TEXT NOT NULL,
  role      TEXT NOT NULL,            -- 'push' | 'block' | 'topic' | 'term'
  rule      TEXT NOT NULL,            -- ★ 어느 규칙이 만들었나
  why       TEXT NOT NULL,            -- 화면에 뜨는 '왜 이어졌나' 한 줄
  evidence  TEXT,                     -- 근거 원문/출처
  built_at  TEXT NOT NULL
);
CREATE UNIQUE INDEX link_key ON link(from_id, to_id, role, rule);
CREATE INDEX link_rule ON link(rule);
```

**`rule` 이 NOT NULL 인 게 핵심이다.** 잘못 이어진 선을 발견했을 때
그 규칙이 만든 선을 전부 찾아 한 번에 지울 수 있다.

```sql
DELETE FROM link WHERE rule = 'topic_by_committee_and_year';
```

규칙 없이 만든 선은 **넣을 수 없다.** 손으로 넣은 선도 `rule='manual'` 을 달고,
`why` 를 반드시 채운다. 근거를 못 대는 선은 주장이지 기록이 아니다.

### 규칙 목록도 테이블로 둔다

```sql
CREATE TABLE rule (
  name       TEXT PRIMARY KEY,
  role       TEXT NOT NULL,
  reads      TEXT NOT NULL,           -- ★ 이 규칙이 읽어도 되는 테이블 (쉼표)
  note       TEXT NOT NULL
);
```

| name | role | reads | 뜻 |
|---|---|---|---|
| `lead_by_rst_proposer` | push | `bill, bill_proposer` | 대표발의자 → 법안 |
| `term_by_promulgation` | term | `bill, president_term` | **공포일 × 재임표만** |
| `topic_by_committee_and_year` | topic | `bill` | 같은 소관위 + 시기 근접 |
| `block_by_vote_split` | block | `vote_member, party_side` | 정당별 찬반이 갈린 경우 |

### 규칙 3 강제 — 대통령은 공포일 × 재임표로만

```sql
CREATE TABLE president_term (
  president TEXT PRIMARY KEY,
  from_dt   TEXT NOT NULL,
  to_dt     TEXT NOT NULL,
  src       TEXT NOT NULL
);
```

`term_by_promulgation` 의 `reads` 는 **`bill, president_term` 두 개뿐이다.**
`bill_proposer` 도 `member` 도 읽지 않는다. 그런 경로를 아예 두지 않는다.

**검사로 강제한다** — 이게 없으면 규칙이 아니라 희망이다.

```
검사 A · role='term' 인 link 는 rule='term_by_promulgation' 뿐이어야 한다
검사 B · 각 규칙의 SQL 원문에 rule.reads 밖의 테이블 이름이 나오면 FAIL
검사 C · role='term' 인 link 를 전부 재계산해서 공포일이 재임 구간 밖이면 FAIL
검사 D · 실패 주입 — 발의자에서 대통령을 끌어오는 가짜 규칙을 넣고
         검사 B 가 실제로 FAIL 하는지 확인한다
```

검사 D 를 반드시 돌린다. **아무것도 안 잡는 검사는 언제나 PASS 라서 가장 오래 산다.**

## 5. 대표발의 · 공동발의를 어떻게 나눌까 — 세 가지 안

지적하신 대로 같은 무게로 두면 법안 하나에 선이 11개 붙는다.
표본 3건의 공동발의자 수는 **10 · 9 · 9명**이었다. 상한 6개를 바로 넘긴다.

의원 쪽은 더 심하다. 22대 의원 한 명이 공동발의한 법안은 **수백 건**이다.

### A안 — 공동발의는 선을 만들지 않는다

창고에는 전부 저장하고, `link` 를 만들지 않는다.

- 지도: 법안당 발의 선 **1개** (대표발의만)
- 카드: "공동발의 10인 · 백선희 신장식 차규근 …" 텍스트로만
- 창고 질의는 그대로 가능 (의원 카드에서 "공동발의 348건" 같은 숫자)

장점: 상한 문제가 사라진다. 대표발의는 **책임이 명확한 공식 기록**이라 `push` 가 맞다.
단점: 공동발의 관계가 지도에서 안 보인다.

### B안 — 공동발의도 선으로 만들되 순위 최하위

`role='cosign'` 을 새로 만들고 상한 계산에서 맨 뒤로 보낸다.

단점: **거의 항상 잘린다.** 화면 결과는 A안과 같은데 계산만 무거워진다.
`link` 행 수도 18,862 × 평균 10 = **약 19만 행**이 늘어난다. 전부 안 보이는 선이다.

### C안 — 공동발의를 선이 아니라 숫자로 표현

법안 노드에 "등 11인" 을 붙이고, 의원 노드에 "공동발의 348건" 을 붙인다.
선은 0개, 정보는 보인다.

### 제안 — **A + C 합본**

`link` 는 대표발의만 만든다 (A). 공동발의는 창고에 전부 있고 카드에 숫자로 뜬다 (C).
B안은 안 한다 — 19만 개의 안 보이는 선은 창고를 무겁게만 만든다.

**단, 공동발의 데이터는 나중에 다른 데 쓴다.**
`PUBL_MONA_CD` 로 "함께 법안을 낸 적이 많은 의원 쌍" 을 셀 수 있다.
이건 발의자·소관부처가 아니라 **행동의 기록**이라 규칙 3 에 걸리지 않는다.
지금 단계에서 하지 않는다. 결과 노드가 19개인 게 병목이지 선이 부족한 게 아니다.

## 6. 규모 판단

### 22대 이전은 몇 건인가 — 아직 모른다. 세는 방법은 있다

확인된 것: **22대 발의법률안 18,862건.**
역대 전부는 **추측하지 않는다.** 22번 호출하면 정확히 셀 수 있다.

```
AGE=1..22 로 pIndex=1&pSize=1 만 호출 → 응답의 list_total_count 를 읽는다
```

호출 22회로 정확한 전체 규모가 나온다. 수집 전에 이것부터 돌린다.

참고로 다른 API 에서 확인된 숫자:
- `VCONFBILLLIST` (회의별 의안목록) **202,346건** — 대수 무관 전체
- `nwbpacrgavhjryiph` (본회의 처리안건_법률안, 22대) **1,681건**

`VCONFBILLLIST` 20만 건은 "회의 × 안건" 조합이라 의안 수가 아니지만,
**전체 규모의 상한 감각**은 준다. 수십만 행 단위다.

### SQLite 가 맞나 — 맞다

| | 값 |
|---|---|
| 예상 행 수 | 가공층 수십만, 원본층 비슷 |
| SQLite 실무 한계 | 수천만 행까지 단일 파일로 무리 없음 |
| 예상 파일 크기 | 원본 gzip 포함 **수백 MB 수준** |
| 동시 쓰기 | 수집기 1개뿐. 경합 없음 |
| 읽기 | 정적 사이트로 내보내므로 **런타임 DB 접근이 아예 없다** |

**결정적인 이유: 이 사이트는 서버가 없다.** 창고는 빌드 때만 쓰고
지도는 정적 JSON 으로 내보낸다. 서버 DB 가 필요한 구조가 아니다.

Postgres 를 쓸 이유는 동시 쓰기·권한·복제인데 셋 다 해당 없다.

### 수집에 며칠 걸리나 — 호출 한도를 모른다

계산할 수 있는 것:

```
pSize 최대 1000 (확인됨)
22대 발의법률안 18,862건 → 19회 호출
의원 3,295명 → 4회
본회의 처리 1,681건 → 2회
                        ─────
22대만                    25회
```

역대 22개 대수면 대략 **수백 회**다. 호출 간격 1초여도 **10분 안쪽**이다.

**확인 못 한 것: 일일 호출 한도.**
열린국회정보에 트래픽 제한이 있는지 문서에서 확인해야 한다.
한도가 있어도 수백 회면 대개 걸리지 않지만, **모르는 채로 돌리지 않는다.**

수집기는 처음부터 이렇게 만든다:
- 호출마다 `raw_fetch` 에 저장하고, **이미 있으면 건너뛴다** (중단 후 재개 가능)
- 호출 간격을 환경변수로 (`PROBE_GAP` 과 같은 방식)
- 한도 초과 응답을 만나면 **멈추고 무엇이 일어났는지 말한다.** 조용히 넘어가지 않는다

## 7. 수집한 전부를 지도에 넣지 않는다

```
창고 18,862건 ──→ 관계가 붙은 것만 ──→ 지도
```

**내보내기 조건을 명시적으로 둔다.**

```sql
CREATE VIEW map_node AS
SELECT b.* FROM bill b
WHERE EXISTS (SELECT 1 FROM link l WHERE l.from_id = b.bill_id OR l.to_id = b.bill_id);
```

그리고 **몇 건이 빠졌는지 항상 밝힌다.**

```
지도  1,204건  ·  창고  18,862건  ·  관계 없어 안 그린 것 17,658건
```

말없이 자르면 "이게 전부" 라는 거짓말이 된다.
`0` 은 의심한다 — 분모를 같이 낸다.

## 8. 아직 못 받은 것

| 서비스 | 상태 | 무엇이 막혔나 |
|---|---|---|
| `nojepdqqaweusdfbi` 국회의원 본회의 표결정보 | ERROR-300 | 필수 요청인자 미상 → 개인별 표결·정당별 집계 불가 |
| `BILLRSNRAW` 법률안 제안이유 및 주요내용 | ERROR-310 | 서비스명 틀림. 카탈로그상 `infId=OS46YD0012559515463` |

### 카탈로그에서 찾은, 아직 안 써본 API

이름만 보고 넣지 않는다. **확인하고 나서 쓴다.**

| 이름 | infId | 왜 중요한가 |
|---|---|---|
| 의안별 표결현황 | `OND1KZ0009677M13515` | 표결의 다른 경로일 수 있다 |
| 의안 제안자정보 | `OOWY4R001216HX11460` | 발의자 전용 API |
| 의안 상세정보 | `OOWY4R001216HX11461` | 법안 본문 |
| 처리 의안통계(발의주체별 법률안) | `OOWY4R001216HX11477` | 규칙 5 (진영 균형) 검증용 |

## 9. 만들 순서

1. **대수별 건수 세기** — `AGE=1..22`, `pSize=1`. 진짜 규모를 먼저 안다
2. **원본층만 만들고 수집** — 매퍼 없이. 원본이 있으면 나머지는 언제든 다시 만든다
3. **매퍼** — `raw_row` → `member` `bill` `bill_proposer`
4. **미매칭 검사** — 위 0장의 SQL. 분모와 함께 출력
5. **규칙 1개만** — `lead_by_rst_proposer`. 검사 A~D 를 먼저 만들고 규칙을 넣는다
6. **내보내기** — 지도/창고 건수를 화면에 밝히며

**5번에서 검사를 먼저 만든다.** 규칙을 넣고 나서 검사를 만들면
그 검사는 지금 있는 데이터를 통과하도록 무의식중에 맞춰진다.
