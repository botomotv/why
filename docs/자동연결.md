# 자동 연결 — 관계선의 뜻을 바꾼다

**설계 판단 문서다. 구현하지 않았고, 데이터도 건드리지 않았다.**

---

## 0. 무엇이 바뀌는가

지금까지 관계선을 **"이것 때문에 저렇게 됐다"** 로 봤다.
그래서 인과 판단은 사람이 해야 하고 자동화가 불가능하다고 정리했었다.

**그게 아니다.** 이 사이트는 인과를 주장하지 않는다.
관련 있는 것들을 이어주고, **판단은 보는 사람이 한다.**

관계선의 뜻이 **"원인"에서 "같은 주제·같은 시기에 있었다"** 로 바뀐다.
그러면 **사실 판정이 가능해지고, 자동 생성이 가능해진다.**

| | 전 | 후 |
|---|---|---|
| 선의 뜻 | A 때문에 B가 됐다 | A와 B가 같은 주제·시기에 있었다 |
| 넣는 근거 | 사람의 인과 판단 | 분야·날짜·소관 같은 **확인 가능한 사실** |
| 규칙 4와의 관계 | 매번 교란 요인을 적어 방어 | **애초에 주장을 안 하므로 방어할 게 없다** |
| 확장 | 사람 손 (병목) | 자동 (병목 해소) |

**이건 후퇴가 아니라 정직해지는 것이다.** 우리는 원래 인과를 증명할 수 없었다.
선이 인과를 주장하지 않으면, 규칙 4를 어길 방법 자체가 줄어든다.

## 1. 지금 role 체계 — 코드에서 읽은 그대로

### 데이터에 저장된 role (`l[3]`) — 4종 + 빈값

| 값 | 건수 | 무엇 | 판단 |
|---|---|---|---|
| `result` | 63 | 인과 후보 | **문제** — 아래 참고 |
| `term` | 60 | 그때 정권 | **기록. 그대로** |
| `lead` | 23 | 대표발의·주도 | **기록. 그대로** |
| `against` | 18 | 반대·대립 | **기록. 그대로** |
| (빈값) | 나머지 | 종류 없음 | 그대로 |

### 화면에 보이는 role (`roleOf()`) — 6종

```js
var ROLE={push:{c:'#6FBF8E',t:'밀어붙임'},  block:{c:'#E2635A',t:'반대·대립'},
          cause:{c:'#7FB2EE',t:'배경·원인'}, effect:{c:'#E3AE55',t:'결과'},
          term:{c:'#A08BC7',t:'그때 정권'},   rel:{c:'#9AA2AE',t:'관련'}};
```

**여기서 가장 중요한 발견이 나온다.**

```js
function roleOf(l,id){
  if(l[3]==='against') return 'block';
  if(l[3]==='term')    return 'term';
  if(l[3]==='lead')    return 'push';
  if(l[5] && l[1]===id) return 'cause';    // ← 데이터에 없다
  if(l[5] && l[0]===id) return 'effect';   // ← 데이터에 없다
  return 'rel';
}
```

**`cause`(배경·원인)와 `effect`(결과)는 데이터에 없다.**
`l[3]='result'` 하나가 **보는 방향에 따라** 만들어진다 —
같은 선이 노드 A에서 보면 "결과", 노드 B에서 보면 "배경·원인"이다.

**즉 인과 주장은 데이터가 아니라 화면 레이어에서 생성된다.**
데이터를 하나도 안 건드리고 **`roleOf`와 `ROLE` 두 곳만 고치면** 뜻이 바뀐다.
이게 이 변경이 싼 이유다.

### 인과를 암시하는 것 — 목록

| 어디 | 무엇 | 왜 문제 | 어떻게 |
|---|---|---|---|
| `ROLE.cause.t` | **"배경·원인"** | '원인' 을 명시적으로 주장 | 이름 교체 (§2) |
| `ROLE.effect.t` | **"결과"** | A→B 방향의 결과라고 주장 | 이름 교체 (§2) |
| `l[3]='result'` | 데이터 값 이름 | 값 이름 자체가 '결과' | 값은 유지, **뜻만 '근거 있는 연결'** 로 재정의 |
| 카드 `이 숫자 앞에 있었던 일` | 인과 사슬 제목 | '앞에 있었던' 은 시간 순서라 **문제 없다** | 그대로 |
| 카드 `그 뒤에 나온 숫자` | 법안 카드의 결과 목록 | 시간 순서 서술 · 경계선 | 그대로 두되 §3 문구를 함께 |
| 카드 `.caution` | "시간 순서일 뿐…" | **이미 정직하다** | 그대로 · 오히려 확대 |
| `l[5]`(evidence) | 있어야 인과 인정 | 이제 '**출처가 붙었다**' 는 뜻으로 재정의 | 의미만 바꿈 |

**`lead` / `against` / `term` 은 손대지 않는다.** 셋 다 공식 기록이다 —
누가 대표발의했는지, 누가 반대 토론했는지, 그때 누가 대통령이었는지.
이건 주장이 아니라 사실이다.

## 2. 관계 이름 대안 — 3개

`cause`/`effect` 를 대체할 이름이다. **셋 다 "무엇이 무엇을 만들었다"고 말하지 않는다.**

### 안 A — 방향을 지우고 하나로 합친다 (권장)

```
cause + effect  →  '같은 주제'   (회색빛 파랑 #7FB2EE)
```

- **가장 정직하다.** 지금 `cause`/`effect` 는 같은 선을 보는 방향만 다른 것이니
  애초에 둘로 나눌 이유가 없었다.
- role 6종 → 5종으로 줄어 화면도 단순해진다.
- **단점**: 시간 순서 정보가 선에서 사라진다. 대신 카드의 `이 숫자 앞에 있었던 일` 이
  연도순으로 보여주므로 정보가 없어지진 않는다.

### 안 B — 시간 순서만 남긴다

```
cause  →  '먼저 있었던 일'   effect  →  '나중에 나온 숫자'
```

- 방향을 유지하면서 인과는 안 주장한다. **시간 순서는 사실이다.**
- **단점**: "먼저 있었으니 원인이겠지" 라는 오해를 완전히 막지는 못한다.
  규칙 4가 경계하는 바로 그 착시다.

### 안 C — 연결의 근거를 이름으로 쓴다

```
'같은 분야'  ·  '같은 시기'  ·  '같은 소관'  ·  '조문에 언급'
```

- **왜 이어졌는지가 선 이름에 그대로 나온다.** 자동 생성 규칙(§4)과 1:1로 대응한다.
- 방문자가 "이건 그냥 같은 분야라서 이어진 거구나" 를 즉시 안다.
- **단점**: role 종류가 늘어 색이 부족하다. 그리고 한 선이 여러 근거를 만족할 수 있다.

### 판단

**A 를 기본으로, C 를 부제로 쓴다.**
선 색·이름은 `'같은 주제'` 하나로 통일하고, 선을 눌렀을 때 **왜 이어졌는지**를
`같은 분야 · 시기 겹침` 처럼 보여준다. A의 단순함과 C의 정직함을 둘 다 가진다.

## 3. 화면이 반복해서 말해야 한다

**사용법에 한 줄 적는 걸로는 부족하다. 아무도 안 읽는다.**
같은 말을 세 군데에서 다른 방식으로 반복한다.

### ① 첫 화면 — 부제 아래 한 줄

지금 부제는 *"왜 이렇게 됐는지 과거 정책을 확인해보세요"* 다.
그 아래(또는 '보는 법' 맨 위)에:

> **선은 "관련 있다"는 뜻입니다. "이것 때문"이라는 뜻이 아닙니다.**

### ② 선을 눌렀을 때 — 가장 중요한 자리

선을 누르면 지금은 아무 일도 안 일어난다. **여기에 작은 말풍선을 띄운다.**

```
같은 주제
임대차 3법  ↔  집값 5.36% 상승
왜 이어졌나 · 같은 분야(부동산) · 시기 겹침(2020)

이 선은 관련이 있다는 표시일 뿐입니다.
어느 쪽이 원인인지는 이 지도가 말하지 않습니다.
```

**"왜 이어졌나"를 반드시 적는다.** 자동 생성이면 규칙 이름이 그대로 근거가 된다.
사람이 이해할 수 있는 형태로 나오지 않는 연결은 **애초에 만들지 않는다.**

### ③ 카드 — 이미 있는 문장을 키운다

`.caution` 에 이미 이렇게 있다:

> 시간 순서일 뿐 인과관계가 증명된 것은 아닙니다. 같은 기간 경제 여건·인구 이동·국제 정세 등
> 다른 요인이 함께 작용했습니다.

**이 문장이 이 사이트에서 가장 정직한 문장이다.** 지금은 접힘 상태에서 잘 안 보인다.
- 관계 목록 **바로 위**로 올린다 (지금은 아래)
- 자동 연결이 섞인 카드에서는 **문구를 바꾼다**:
  *"아래 항목들은 같은 주제·시기라서 이어졌습니다. 인과관계를 뜻하지 않습니다."*

### ④ 자동/수동을 구분해서 표시한다

사람이 근거를 확인해 넣은 연결과 규칙이 자동으로 만든 연결은 **신뢰도가 다르다.**
자동 연결에 작은 표시를 단다 (지금 `내가 이음` 표시와 같은 방식).

**강제:** 검사에 넣는다 — 자동 생성 연결에 "왜 이어졌나" 근거가 없으면 FAIL.

## 4. 자동 연결 규칙 — 무엇과 무엇을 잇나

### 후보 규칙과 위험

| 규칙 | 사실인가 | 위험 | 판단 |
|---|---|---|---|
| **같은 분야 + 시기 겹침** | ○ 둘 다 데이터에 있다 | **폭발한다.** 부동산 법안 수백 개 × 결과 몇 개 | 단독으로 쓰면 안 된다 |
| **법 조문이 그 통계를 언급** | ○ 원문에서 확인 가능 | 언급이 드물다. 재현율이 낮다 | **가장 강한 근거.** 최우선 |
| **소관부처가 같음** | ○ 의안정보에 있다 | 부처 하나가 수천 건을 담당 | 단독 불가. 보조 조건 |
| **시행일이 통계 변곡점 근처** | △ '변곡점' 정의가 우리 판단 | **위험.** 변곡점을 우리가 고르면 그게 인과 주장이다 | **쓰지 않는다** |

**네 번째는 빼야 한다.** "변곡점 근처"를 우리가 정하는 순간
"이 법이 이 변화를 만들었다"고 고르는 셈이 된다. 규칙 4로 되돌아간다.

### 그래서 — 점수제가 아니라 관문제

"얼마나 가까워야 잇는가"를 **점수 합산으로 풀면 안 된다.**
점수는 임계값을 우리가 정하는 것이고, 그 숫자가 곧 인과 판단이 된다.

대신 **관문(gate)** 으로 푼다. 각 관문은 예/아니오로 답할 수 있는 사실이다.

```
1관문 · 분야가 겹치는가            (cats 교집합 ≥ 1)
2관문 · 시기가 겹치는가            (법 시행일 ~ 통계 기준연도, 아래 창 참고)
3관문 · 아래 중 하나 이상인가
        · 법 조문·제안이유가 그 통계·지표를 언급한다
        · 소관부처가 같다
        · 이미 사람이 이은 연결과 같은 쌍이다
```

**세 관문을 모두 통과한 것만 잇는다.** 3관문이 "그냥 같은 분야"를 걸러낸다.

**시기 창(window)** 은 자의적일 수밖에 없으므로 **가장 넓게 잡고 화면에 밝힌다.**
법 시행일이 통계 기준연도의 **±3년** 안. 근거: 통계가 연 단위로 나오고
법 시행 효과가 반영되기까지 통상 1~2년이 걸린다. **이 숫자는 우리가 정한 것이라고 문서와 화면에 적는다.**

### 그래도 넘치면 — 상한을 둔다

관문을 통과해도 결과 노드 하나에 수십 개가 붙을 수 있다.
**상한을 두고, 잘라낸 개수를 반드시 화면에 밝힌다.**

```
지도에는 가까운 것 6개만 그렸습니다. (관련 항목 34개)   [전부 보기]
```

**말없이 자르지 않는다.** 자른 것을 숨기면 "이게 전부"라는 거짓말이 된다.
CLAUDE.md 의 "0은 의심한다 · 분모를 같이 출력한다"와 같은 원칙이다.

상한 안에서 무엇을 남길지는 **읽을 수 있는 순서**로 고른다 —
① 사람이 이은 것 ② 조문에 언급된 것 ③ 소관 같은 것 ④ 시기가 가까운 것.

## 5. 몇 개까지 읽을 수 있나 — 실측

**추측하지 않고 지금 코드로 실제로 그려서 쟀다.**
`집값 5.36% 상승`(1440×900)에 가짜 연결을 붙여가며 측정했다.

- **이웃** = 포커스 시 1단계로 그려진 노드 수
- **읽힘** = 이름표가 다른 이름표와 하나도 안 겹친 노드 수
- **최소각도** = 중심에서 이웃으로 나가는 선들의 인접 각도 최솟값

| 이웃 | 이름표 겹침(쌍) | 읽힘 | 읽힘 비율 | 최소각도 |
|---:|---:|---:|---:|---:|
| 4 | 0 | 4 | **100%** | 20.1° |
| 6 | 0 | 6 | **100%** | 20.1° |
| 8 | 2 | 5 | 63% | 10.3° |
| 10 | 5 | 4 | 40% | 3.2° |
| 11 | 6 | 3 | 27% | 3.2° |
| 13 | 9 | 2 | **15%** | 3.2° |

**임계점은 6~7개다.**
- **6개까지 100%** 읽힌다. 선 간격도 20°로 넉넉하다.
- **8개에서 63%로 급락**한다. 여기가 무너지는 지점이다.
- 10개를 넘으면 최소각도가 3.2°로 붙어 **선을 눈으로 구분할 수 없다.**
- 13개 이후로는 붙인 선을 20개, 32개로 늘려도 **이웃이 13에서 멈춘다** —
  화면 렌더에 이미 상한이 걸려 있다. 그런데도 읽힘은 15%다.
  **말없이 잘리고 있고, 남은 것도 못 읽는다.** 지금도 이미 나쁜 상태다.

### 참고 — 지금 데이터

결과 노드 19개의 연결 수는 **평균 2.8개, 최대 8개**(합계출산율 0.7명대)다.
전체 최대는 `이재명` 35개.

**즉 지금도 상위 노드는 이미 임계점 위에 있다.**
자동 연결을 켜면 즉시 무너진다.

### 결론 — 상한은 6

**지도에 그리는 선은 결과 노드 하나당 6개를 넘지 않는다.**
7개째부터는 카드의 목록으로 보낸다. 카드는 스크롤되므로 개수 제한이 필요 없다.

**지도는 6개, 카드는 전부, 잘린 개수는 항상 표시.**

## 6. 착수 순서

이 변경은 **데이터를 안 건드리고 화면 레이어만 고치면** 절반이 끝난다.
`roleOf()` 와 `ROLE` 두 곳이다.

```
1. 이름·색 바꾸기        roleOf / ROLE — 데이터 무변경, 하루
2. 화면에서 반복하기      선 클릭 말풍선 · caution 위치 · 첫 화면 한 줄
3. 상한 6개 + 잘린 수 표시  이게 없으면 자동 연결을 켤 수 없다
4. 이름표 겹침 해소       지금도 280~290쌍이다. 자동 연결 전에 풀어야 한다
5. 창고(SQLite) 분리      자동 연결은 '왜 이어졌나' 를 행마다 저장해야 한다
6. 자동 연결 켜기         관문 3개 + 상한 6개
```

**3번과 4번을 건너뛰고 6번을 하면 사이트가 죽는다.** 실측이 그렇게 말한다.

**그리고 5번이 생각보다 중요하다.** 자동 연결은 선마다
"어느 규칙이 이걸 만들었는가"를 저장해야 한다. 그게 없으면
잘못 이어진 것을 찾아 고칠 방법이 없고, §3-②의 "왜 이어졌나"도 못 보여준다.
`index.html` 한 파일로는 감당이 안 된다.

---

## 7. 바뀌지 않는 것

- **규칙 1** 확정된 공식 기록만 — 그대로. 자동 연결도 확인된 사실로만 잇는다.
- **규칙 3** 재임 ≠ 밀어붙임 — 그대로. `term` 은 손대지 않는다.
- **규칙 4** 시간 순서를 인과로 단정하지 않는다 — **오히려 강해진다.**
  선이 인과를 주장하지 않으면 어길 방법이 줄어든다.
- **규칙 7** 모든 노드에 출처 — 그대로. 여기에 하나 더한다:
  **자동 연결에는 "왜 이어졌나"가 출처 역할을 한다.**

# 부록 · 관문 3개 설계 (2026-08 · 창고 실측 기준)

**설계만 한다. 구현은 표결 수집이 끝난 뒤다.**

앞의 4장이 관문의 뜻을 정했다. 여기서는 **실제 데이터로 돌아가는지**를 재고
각 관문의 입력·판정·산출을 못 박는다.

## 0. 먼저 — 데이터가 관문을 받쳐 주는가

창고에 담긴 것으로 필드 채움률을 쟀다. 추정이 아니라 실측이다.

| 필드 | 어디에 | 채움 |
|---|---|---:|
| `BILL_NAME` 법안명 | 발의법률안 | 99,995 / 99,995 (100%) |
| `COMMITTEE` 소관위 | 발의법률안 | 99,493 / 99,995 (99.5%) |
| `PROPOSE_DT` 발의일 | 발의법률안 | 99,995 (100%) |
| `PROC_RESULT` 처리결과 | 발의법률안 | 85,916 (86%) |
| **`ANNOUNCE_DT` 공포일** | **본회의 처리안건** | **18,158 / 75,983 (24%)** |

**공포일 24% 는 결함이 아니다.** 공포일은 **가결돼 실제로 법이 된 것**에만 있다.
본회의 처리안건의 가결 합계(원안 11,222 + 수정 7,359 = 18,581)와 거의 같다.

그래서 이것이 **2관문의 핵심 원칙**이 된다 —
**효력이 생긴 법만 잇는다.** 통과 못 한 법안은 통계를 바꿀 수 없다.
따로 거를 필요 없이 공포일이 없으면 후보에서 빠진다.

## 1. 세 관문 — 입력과 판정

### 1관문 · 분야가 겹치는가

| | |
|---|---|
| 법안 쪽 | `COMMITTEE_NM` (소관위) · **본회의 처리** 표 |
| 결과 쪽 | 지도의 분야(`cat`) |
| 판정 | 소관위 → 분야 대응표에서 교집합이 1개 이상 |

**대응표는 우리의 편집 판단이다.** 그래서 표로 두고 근거를 적는다.
코드에 박지 않는다 — `party_side` 와 같은 방식이다.

```sql
CREATE TABLE cat_committee (
  cat       TEXT NOT NULL,   -- 지도의 분야
  committee TEXT NOT NULL,   -- 소관위 이름 그대로
  src       TEXT NOT NULL,   -- 왜 이렇게 묶었나
  PRIMARY KEY (cat, committee)
);
```

**1관문만으로는 못 쓴다.** 실측: 보건복지위원회 하나가 10,590건이다.

### 2관문 · 시기가 겹치는가

| | |
|---|---|
| 법안 쪽 | **공포일**(`ANNOUNCE_DT`) · **본회의 처리** 표. 없으면 후보에서 빠진다 |
| 결과 쪽 | 결과 노드의 기준연도(`yr`) |
| 판정 | 공포일이 기준연도 **±3년** 안 |

**세 관문이 전부 '본회의 처리' 표를 읽는다.** 2관문이 공포일을 쓰는데 그 필드가
그 표에만 있기 때문이다. 같은 표에서 읽어야 조인이 하나로 끝나고,
`BILL_NAME`/`BILL_NM` 처럼 이름만 다른 필드를 헷갈릴 일도 없다
(세 쌍의 목록은 docs/창고설계.md '필드 출처 표').

**발의일이 아니라 공포일을 쓴다.** 발의는 효력이 없다.
그리고 공포일은 규칙 3(대통령 관계)이 쓰는 것과 **같은 필드**다 — 기준이 하나여야 한다.

**±3년은 우리가 정한 숫자다.** 통계가 연 단위로 나오고 법 시행 효과가
반영되기까지 통상 1~2년이 걸린다는 것이 근거다.
**이 숫자를 화면에 적는다.** 안 적으면 우리가 고른 창을 사실인 척하는 것이 된다.

### 3관문 · 근거가 있는가

**이게 결정적인 관문이다.** 앞의 두 개는 "같은 동네에 있었다" 까지만 말한다.

| | |
|---|---|
| 법안 쪽 | `BILL_NM` (법안명) · **본회의 처리** 표 |
| 결과 쪽 | 결과 노드의 **핵심어 목록**(새 필드 `keys`) |
| 판정 | 법안명이 핵심어 중 하나를 포함 |

원래 3관문에 두려던 나머지 두 다리는 **뺀다.**

- **"제안이유가 언급"** — `BILLRSNRAW` 가 `ERROR-310`(서비스명 틀림)이라 지금 못 받는다.
  이름을 찾으면 되살린다. 그때는 법안명보다 강한 근거가 된다.
- **"소관부처가 같음"** — 결과 노드에는 소관부처가 없다. 붙이려면 우리가 정해야 하는데,
  그건 1관문과 같은 판단을 두 번 하는 것이다. **독립된 근거가 아니다.**
- **"사람이 이미 이은 쌍"** — 이건 자동 연결이 아니라 이미 있는 선이다. 관문을 통과할 필요가 없다.

**핵심어 목록도 우리의 편집 판단이다.** 그래서 **화면의 "왜 이어졌나" 한 줄에 그대로 쓴다.**

```
왜 이어졌나 · 법안명에 '출산' 이 들어감 · 공포 2022년 (결과 2023년, 1년 차이)
```

## 2. 관문이 실제로 얼마나 거르나 — 실측

창고의 공포된 법안 18,158건으로 세 결과 노드를 시뮬레이션했다.

| 결과 노드 | 2관문만 | 1+2 | 2+3 | **1+2+3** |
|---|---:|---:|---:|---:|
| 합계출산율 0.7명대 (2023 · 보건복지) | 5,006 | 268 | 27 | **9** |
| 집값 5.36% 상승 (2020 · 국토교통) | 5,358 | 367 | 130 | **48** |
| 전기요금 인상 약 40% (2023 · 산자중기) | 5,006 | 225 | 144 | **23** |

읽을 것:

- **관문 하나로는 전부 못 쓴다.** 2관문만이면 5천 건, 1+2 도 수백 건이다
- **3관문이 가장 세게 거른다.** 268 → 9 (30배)
- **그래도 상한 6개를 넘는다.** 9·48·23 전부 넘는다 → **잘린 개수를 반드시 밝힌다**
- 집값 48건은 부동산 법안이 원래 많아서다. 분야마다 다르다는 것도 화면에 드러나야 한다

## 3. 산출 — 통과·탈락을 분모와 함께

**말없이 거르면 "이게 전부" 라는 거짓말이 된다.** 실행할 때마다 이 표를 낸다.

```
자동 연결 · 결과 노드 19개 대상

  후보 (공포된 법안)          18,158건
  1관문 분야 겹침              4,912건   탈락 13,246
  2관문 시기 ±3년                812건   탈락  4,100
  3관문 법안명에 핵심어           137건   탈락    675
  ────────────────────────────────────
  이은 선                        137건
  상한 6개로 잘린 것              41건   ← 화면에 '+N' 으로 표시
```

세 가지를 지킨다.

1. **각 관문의 탈락 수를 따로 낸다.** 합계만 내면 어느 관문이 일하는지 모른다
2. **0 은 의심한다.** 어떤 결과 노드가 0건이면 그 노드 이름을 찍는다 —
   "핵심어를 안 넣었다" 인지 "정말 없다" 인지 구별해야 한다
3. **상한으로 자른 개수는 화면에 낸다.** 검사 17번이 이미 강제하고 있다

## 4. 만들어진 선의 모양

```
link.from_id  = 법안 노드
link.to_id    = 결과 노드
link.role     = 'topic'          ← 'push' 아니다. 관련이지 인과가 아니다
link.rule     = 'topic_by_name_and_date'
link.why      = "법안명에 '출산' 이 들어감 · 공포 2022년 (결과 2023년, 1년 차이)"
link.evidence = 의안 상세 URL
```

- `role` 은 **반드시 `topic`**. `push`(밀어붙임)는 대표발의처럼 공식 기록이 있을 때만이다
- `rule` 과 `why` 는 `NOT NULL` — 스키마가 이미 막고 있다
- `rule.reads` 는 `bill, result_key` 둘뿐이다. **대통령·발의자 표를 읽지 않는다**

## 5. 만들기 전에 정할 것

1. **핵심어를 누가 넣나.** 결과 노드 19개에 `keys` 를 손으로 넣어야 한다.
   19개면 할 만하다. 결과가 늘면 그때 다시 본다
2. **분야↔소관위 대응표.** 지금 분야 칩과 소관위 15개 이상을 맞춰야 한다
3. **±3년을 화면 어디에 쓰나.** '왜 이어졌나' 줄에 매번 쓰면 길다.
   선 카드 머리에 한 번 쓰는 쪽이 나아 보인다
4. **집값처럼 48건이 나오는 분야를 어떻게 보여줄까.**
   6개만 그리고 42개를 목록으로 빼는 것이 지금 설계다

## 6. 안 하는 것

- **점수 합산.** 임계값을 우리가 정하는 순간 그 숫자가 인과 판단이 된다
- **시행일이 통계 변곡점 근처인지 보기.** 변곡점을 우리가 고르면 그게 주장이다
- **발의일로 잇기.** 통과 못 한 법안은 통계를 바꿀 수 없다
- **방향으로 뜻 만들기.** 어느 쪽이 앞인지로 원인·결과를 가르지 않는다

# 부록 2 · 창고 전량 실측이 설계를 바꾼 것 (2026-08-25)

## 1. `against` 를 표결로 만들 수 없다

22대 개인별 표결 183,508행 · 620개 법안을 다 보고 센 결과다.

| | 건수 | 620건 대비 |
|---|---:|---:|
| 반대 0표 | **427** | 68.9% |
| 반대 1~4표 | 145 | 23.4% |
| 반대 5~19표 | 34 | 5.5% |
| 반대 20~49표 | 8 | 1.3% |
| 반대 50~99표 | 6 | 1.0% |
| 반대 100표 이상 | **0** | 0% |

- 반대율 10% 이상 : **12건**
- 만장일치(반대 0 · 기권 0) : 139건
- 두 거대 정당의 **방향이 갈린 법안** : **9건**

**9건으로는 관문을 만들 가치가 없다.** 자동 규칙 하나를 유지하는 비용이
그 규칙이 만드는 선 9개보다 크다.

## 2. 한국 국회의 대립은 반대표가 아니라 **불참**으로 나타난다

| 정당 | 불참율 |
|---|---:|
| 국민의힘 | **39.3%** (25,937/65,976) |
| 무소속 | 36.1% |
| 개혁신당 | 31.5% |
| 더불어민주당 | **16.6%** (16,697/100,674) |

두 거대 정당의 불참율이 **50%p 이상 벌어진 법안 62건.**
한쪽이 100% 불참한 사례가 여럿이다. 방향이 갈린 9건의 **7배**다.

**그래도 불참으로 `against` 를 만들지 않는다.**
불참은 출장·질병·지역구 일정도 불참이다. 100% 불참은 보이콧이 거의 확실하지만
"거의 확실" 은 사실 판정이 아니다. 시간 순서를 인과로 단정하지 않는다는 규칙 4 와 같은 종류다.

### 그래서 정한 것

- **표결로는 선을 만들지 않는다.** `against` 는 지금처럼 공식 기록(반대 성명·
  위헌심판 청구·폐지 법안)에서만 손으로 넣는다
- **표결은 카드에 숫자로 넣는다.** "본회의 표결 · 찬성 251 · 반대 3 · 기권 1 ·
  불참 45 (국민의힘 불참 92%)" 는 사실이고, 판단은 보는 사람이 한다
### 나중에 선으로 만든다면 이름은 `split` 이다 — 결정 기록

`against` 는 **"반대·대립했다"** 는 뜻이고 공식 기록(반대 성명·위헌심판 청구·폐지 법안)에서만 온다.
표결이 갈린 것은 그것과 다른 사실이다. **투표가 갈렸다는 것이지 대립했다는 판정이 아니다.**
같은 이름을 쓰면 손으로 넣은 63건과 자동 9건이 화면에서 구별되지 않고,
"반대했다" 로 읽히면서 우리가 안 한 판정을 한 것이 된다.

| | `against` | `split` (아직 안 만듦) |
|---|---|---|
| 뜻 | 반대·대립한 공식 기록 | 본회의 표결에서 두 정당의 방향이 갈렸다 |
| 출처 | 사람이 넣는다 | 개인별 표결 |
| 근거 문장 | 그 기록 자체 | "민주 166 찬성 / 힘 85 반대" 같은 실제 숫자 |
| 지금 건수 | 63 | **9** |

**9건이라 지금은 안 만든다.** 규칙 하나를 유지하는 비용이 그 규칙이 만드는 선 9개보다 크다.
21·20대를 받은 뒤 다시 세어 보고, 그때도 두 자리 수면 계속 안 만든다.

## 3. `ANNOUNCE_DT`(공포일)는 발의법률안이 아니라 **본회의 처리** 표에 있다

2관문과 규칙 3 이 쓰기로 한 필드다. 발의법률안(`nzmimeepazxkubdpn`) 응답에는 **없다.**
본회의 처리(`nwbpacrgavhjryiph`) 에 75,983행 전부 들어 있고, 그중 공포일이 채워진 것이 **18,158건**이다.

**BILL_ID 로 조인해야 한다.** 이 문서가 필드 이름만 적고 어느 표에 있는지 안 적어서
구현 직전까지 몰랐다 — CLAUDE.md 의 "문서에 조건을 쓰면 그 조건이 코드 어디에 있는지 같이 적는다" 가 이것이다.

## 4. 수집 후보 목록이 절반을 놓치고 있었다

표결을 물어볼 `BILL_ID` 를 발의법률안에서만 꺼냈다.

| 20~22대 | 건수 |
|---|---:|
| 본회의 표결(집계 있음) | 7,647 |
| 그중 발의법률안 목록에 있음 | 3,420 |
| **발의법률안 목록에 없음** | **4,227 (55%)** |

없는 것들의 제안자: 정부 605 · 보건복지위원장 449 · 농림축산식품해양수산위원장 410 …
즉 **위원회 대안**이다. 여러 법안을 합쳐 실제로 통과하는 것이 대안이고
(대안반영폐기 24,844건이 그 증거), 지도가 다루려는 큰 법은 대부분 그쪽이다.

거꾸로 본회의 처리 표만 쓸 수도 없다 — 22대에서 개인별 표결이 있는 620건 중
**8건이 본회의 처리 표에 아예 없었다.** 어느 한쪽도 완전하지 않다.

`nqfvrbsdafrmuzixe`(의안접수목록)도 같다. 인증키가 있는 자리에서 파라미터를 찾아봐야 한다.

## 법제처 — 받을 수 있다

`lawService.do` 응답 최상위 키: `개정문 · 법령키 · 기본정보 · 부칙 · 조문 · **제개정이유**`

```
제개정이유내용:
  [일부개정]

    노후소득을 보장하고 취업유인을 제고하기 위하여 소득활동에 따른 노령연금액 감액
    대상에서 초과소득월액이 200만원 미만인 사람을 제외하고 …
  <법제처 제공>
```

### 자동 법률 62개 실측

| | |
|---|---:|
| 법제처에서 이름이 정확히 맞는 것 | **58 / 62** |
| 그중 **제·개정이유가 있는 것** | **57** |
| 이유 글자 수 (중앙값 / 최대) | 387자 / 2,476자 |

못 찾은 4개 중 3개는 **가운뎃점 문자가 다르다.**
법제처는 `ㆍ`(U+318D), 국회는 `·`(U+00B7) 를 쓴다 —
`저출산ㆍ고령사회기본법` · `신에너지 및 재생에너지 개발ㆍ이용ㆍ보급 촉진법` ·
`토지이용 인ㆍ허가 절차 간소화를 위한 특별법`.
**정규화하면 60/62 가 된다.**
남는 하나는 `공소청법`(2026 신설)으로 법제처 현행법령에 아직 없다 — "확인 중" 으로 비운다.

## 한계 — 반드시 밝혀야 한다

**법제처는 현행 법령만 준다.** 그래서 `제개정이유` 는 **가장 최근 개정 하나**의 이유다.
우리 노드가 `국민연금법 · 2022~2025년 공포 6건` 이면 그 6건 중 마지막 것만 설명된다.
나머지 5건의 이유는 받을 방법이 지금 없다.

그러니 화면에는 이렇게 적어야 한다 —
**"아래는 가장 최근 개정(2025-12-16)의 이유입니다. 그 앞 5번의 개정 이유는 아직 못 받았습니다."**

## 법 이름 자르기를 고쳤다 — 52/65 → 60/62

`법률안$` 를 `법` 으로 바꾸고 있었다. 그래서
`중대재해 처벌 등에 관한 법률안` 이 **`중대재해 처벌 등에 관한법`** 이 됐고 법제처에서 못 찾았다.
제정안 이름 끝은 두 가지다 — `…법률안`(→ 법률) 과 `…법안`(→ 법). **긴 것부터 자른다.**
이 이름은 화면에도 그대로 나가고 있었다.
